============================================================
1) المقصود بإعدادات التشغيل هنا
============================================================

هذه الدراسة لا تتكلم عن مسارات التطبيق أو البورتات، بل عن الإعدادات التي يغيرها المدير/المطور من داخل قوائم النظام وتؤثر مباشرة على العمل اليومي:

- من يستقبل العميل.
- من يأخذ الطلب.
- هل الطاولة مقفولة على كابتن واحد أم مفتوحة لأي جرسون طلبات.
- من يستلم من المطبخ.
- من يطلب الشيك.
- متى تبدأ دورة التنظيف.
- هل يلزم جدول ورديات قبل دخول المستخدم.
- ما دور المستخدم اليوم مقارنة بدوره الأساسي.
- إعدادات الجهاز المشترك والـ PIN.
- إعدادات المطبخ والطباعة.
- إعدادات VIP/Owner.
- إعدادات الضريبة والخدمة.
- نوع المنشأ: مطعم أو كوفي شوب.

المصدر الرئيسي:
- صفحة إعدادات التشغيل الشاملة.
- صفحة دورة العمل ومسارات الأدوار.
- صفحة جدولة أدوار المستخدمين.
- صفحة إعدادات تشغيل نقطة البيع.
- صفحة سياسة الضريبة والخدمة.
- صفحة نوع المنشأ.

3) الأدوار الأساسية في النظام
============================================================

الأدوار المعروفة في الواجهة:

- cashier = كاشير
- accountant = محاسب
- manager = مدير
- developer = مطوّر
- host = جارسون الاستقبال
- waiter = جارسون الطلبات
- kitchen = مطبخ
- speed_order = الطلبات السريعة
- server = جارسون المناولة
- kids_guard = كيدز إيريا

كل دور له شاشة دخول افتراضية:

- cashier -> /app/cashier
- accountant -> /app/accountant
- manager -> /app/manager
- developer -> /app/developer
- host -> /app/host
- waiter -> /app/waiter/tables
- kitchen -> /app/kitchen
- speed_order -> /app/speed_order
- server -> /app/server
- kids_guard -> /app/kids-guard

المعنى اليومي:
- دور المستخدم ليس مجرد اسم؛ هو يحدد أين يدخل وماذا يرى وما العمليات المتوقعة منه.
- لكن الدور الفعّال قد يتغير يومياً عبر جدولة أدوار المستخدمين.

============================================================
4) الدور الأساسي مقابل الدور المجدول
============================================================

كل مستخدم له دور أساسي في MAT3AM_APP_USERS.
مثال:
- أحمد دوره الأساسي waiter.
- محمد دوره الأساسي host.

لكن في صفحة “جدولة أدوار المستخدمين” يمكن تحديد فترة زمنية لدور مختلف.
مثال:
- أحمد من 2026-05-20 إلى 2026-05-20 دوره server.

عند تسجيل الدخول:
1. النظام يبحث عن صف في MAT3AM_USER_ROLE_SCHEDULE يغطي تاريخ اليوم.
2. إذا وجد صفاً، يستخدم الدور المجدول كدور فعّال.
3. إذا لم يجد صفاً، يستخدم الدور الأساسي.
4. إذا وجد أكثر من صف متداخل لنفس اليوم، يستخدم الأحدث إنشاءً.

مثال عملي:
- مستخدم أساسي waiter.
- يوجد له جدول اليوم كـ cashier.
- عند الدخول اليوم يتعامل النظام معه ككاشير.
- غداً إذا انتهت الفترة يرجع لدوره الأساسي waiter.

تأثير اختيار الدور في الجدولة:
- اختيار waiter يجعله جرسون طلبات لذلك اليوم.
- اختيار host يجعله استقبال لذلك اليوم.
- اختيار server يجعله مناولة لذلك اليوم.
- اختيار kitchen يجعله مطبخ لذلك اليوم.
- اختيار cashier يجعله كاشير لذلك اليوم.

ملاحظة مهمة:
- تعديل الجدولة لا يغير الدور الأساسي المحفوظ في بطاقة المستخدم.
- هو يغير الدور الفعّال وقت تسجيل الدخول خلال الفترة.

============================================================
5) إلزام وجود جدولة لليوم قبل الدخول
============================================================

الإعداد:
- enforceRoleScheduleForShift

مكانه:
- إعدادات التشغيل الشاملة -> الوردية وجدولة الأدوار.

الاختيارات:

1. معطّل off
-------------
الأثر:
- المستخدم يستطيع الدخول بدوره الأساسي حتى لو لا توجد له جدولة اليوم.
- الجدولة إذا وجدت تطبق وتغير الدور الفعّال.
- إذا لم توجد، لا يمنع الدخول.

مناسب لـ:
- التشغيل المرن.
- بداية التطبيق.
- مطعم لا يريد إلزام الورديات بدقة.

2. مفعّل on
------------
الأثر:
- بعض أدوار الصالة لا يسمح لها بالدخول إلا لو لها صف جدولة يغطي تاريخ اليوم.
- الأدوار المتأثرة صراحة في الكود:
  - waiter
  - host
  - server
  - speed_order

إذا لم توجد جدولة:
- تظهر رسالة: أنت لست ضمن فريق العمل اليوم

مناسب لـ:
- مطعم يريد منع أي جرسون غير موجود في وردية اليوم من الدخول.
- تشغيل يومي منظم.

ملاحظة:
- المدير والمطور والكاشير/المحاسب لا يدخلون ضمن نفس مجموعة أدوار الصالة المذكورة في شرط الإلزام، إلا إذا تغير منطق النظام لاحقاً.

============================================================
6) من يستقبل العميل عند الدخول
============================================================

المفتاح:
- receiveGuestBy

الاختيارات:
- host = جارسون الاستقبال
- manager = مدير المطعم
- waiter = جارسون الطلبات
- customer_self = العميل نفسه
- server = جارسون المناولة

الأثر:
- يحدد الدور المتوقع أن يبدأ رحلة العميل عند الوصول.
- يستخدمه النظام لمعرفة لمن توجه مهمة استقبال العميل في دورة العمل.

اختيار host:
- الاستقبال هو المسؤول الطبيعي عن بداية الجلسة.
- مناسب لمطعم فيه هوست أو استقبال.

اختيار manager:
- المدير يتدخل في بداية الجلسة.
- مناسب لتشغيل محدود أو مطعم صغير أو فترات خاصة.

اختيار waiter:
- جرسون الطلبات يبدأ التعامل من أول دخول العميل.
- مناسب لمطعم بدون استقبال منفصل.

اختيار customer_self:
- العميل نفسه يبدأ العملية.
- مناسب لتصورات QR أو self-service.

اختيار server:
- جرسون المناولة يبدأ الاستقبال.
- أقل شيوعاً، مناسب لو دور المناولة مدمج مع الاستقبال.

الافتراضي:
- host

============================================================
7) من يأخذ طلبات العميل
============================================================

المفتاح:
- takeOrderBy

الاختيارات:
- host
- manager
- waiter
- customer_self
- server

الأثر:
- يحدد الدور الرئيسي المتوقع لإدخال الطلبات على الطاولة.

اختيار waiter:
- جرسون الطلبات هو المسؤول الأساسي.
- هذا هو الافتراضي والاختيار الأكثر طبيعية.

اختيار host:
- الاستقبال يأخذ الطلبات.
- مناسب لمنشأة صغيرة أو كوفي شوب حيث نفس الشخص يستقبل ويأخذ الطلب.

اختيار manager:
- المدير يأخذ الطلبات.
- مناسب لحالات خاصة وليس تشغيل يومي كبير.

اختيار customer_self:
- العميل يأخذ الطلب بنفسه.
- مناسب لمسار طلب ذاتي مستقبلاً.

اختيار server:
- جرسون المناولة يأخذ الطلب.
- مناسب عندما لا يوجد فصل بين من يأخذ الطلب ومن يناول.

============================================================
8) قفل الطاولة على كابتن واحد
============================================================

المفتاح:
- orderTakerExclusiveTable

الاختيارات:

1. off = لا، أي جرسون طلبات يعمل على الطاولة
---------------------------------------------
الأثر:
- أي waiter يستطيع إرسال طلبات أو طلب الحساب على نفس الطاولة.
- لا يوجد منع بناءً على الكابتن المسكّن.

مناسب لـ:
- المطاعم التي يعمل فيها كل الجرسونات على كل الطاولات.
- فترات الذروة التي تحتاج مرونة.

المخاطر:
- قد يحدث تداخل بين أكثر من جرسون على نفس الطاولة.
- صعوبة تحديد المسؤول عن أخطاء الطلب.

2. on = نعم، قفل حتى تقفيل الحساب
----------------------------------
الأثر:
- إرسال الطلبات وطلب الحساب مسموح فقط للمستخدم الذي تم تسكينه ككابتن على الجلسة.
- المدير والمطور مستثنيان.
- إذا حاول جرسون آخر العمل، تظهر رسالة أن الطاولة مسندة لكابتن آخر.

مناسب لـ:
- مطعم يعتمد على مسؤولية واضحة لكل طاولة.
- نظام عمولات أو محاسبة حسب كابتن.
- منع التضارب في الطلبات.

المخاطر:
- إذا نسي المدير تغيير الكابتن عند تبديل الوردية، قد يتعطل الجرسون الجديد.
- يحتاج إجراء واضح: تسكين كابتن أو تدخل المدير.

الافتراضي:
- off

============================================================
9) من يستلم من المطبخ ويوصل للطاولات
============================================================

المفتاح:
- deliverFromKitchenBy

الاختيارات:

1. server = جرسون مناولة
-------------------------
الأثر:
- مهمة استلام الطلب من المطبخ وتوصيله للطاولة توجه للمناولة.
- مناسب لمطعم يفصل بين الكابتن والمناولة.

2. waiter = نفس جرسون الطلبات
-----------------------------
الأثر:
- نفس الجرسون الذي يأخذ الطلب هو من يتابع استلامه وتوصيله.
- مناسب لمطاعم صغيرة أو كوفي شوب.

3. manager = مدير المطعم
------------------------
الأثر:
- المدير هو المسؤول عن الاستلام/التوجيه.
- غير مناسب غالباً للتشغيل اليومي المكثف، لكنه مفيد في تشغيل خاص.

4. host = جرسون الاستقبال
--------------------------
الأثر:
- الاستقبال يدخل في التسليم.
- مناسب فقط لو الأدوار مدمجة.

5. kitchen_window = استلام مباشر من نافذة الشيف
-----------------------------------------------
الأثر:
- لا يوجه الاستلام لدور صالة محدد.
- يفترض أن المطبخ/نافذة الشيف تسلم مباشرة.

الافتراضي:
- server

============================================================

اختيار manager:
- المدير يعتمد أو ينفذ طلب الحساب.
- مناسب لرقابة قوية أو مطاعم صغيرة.

اختيار server:
- المناولة مسؤولة عن طلب الشيك.
- مناسب لو المناولة هي حلقة التعامل النهائي مع العميل.

============================================================
12) متى يبدأ التنظيف تلقائياً
============================================================

المفتاح:
- cleaningStartTrigger

الاختيارات:

1. request_check = عند طلب الحساب
---------------------------------
الأثر:
- بمجرد طلب الحساب يبدأ مسار تجهيز الطاولة للتنظيف.
- قد يكون مبكراً لو العميل لا يزال جالساً.

مناسب لـ:
- مطعم سريع الدوران.
- حالة تجهيز فريق النظافة مبكراً.

2. payment_completed = عند إتمام الدفع
--------------------------------------
الأثر:
- التنظيف يبدأ بعد الدفع.
- هذا هو الأكثر أماناً لأن الجلسة انتهت مالياً.

مناسب لـ:
- أغلب المطاعم.

الافتراضي:
- payment_completed

3. manager_command = بأمر مباشر من المدير
-----------------------------------------
الأثر:
- لا يبدأ التنظيف تلقائياً إلا إذا المدير نفذ أمر مباشر.
- مناسب لمن يريد تحكم يدوي كامل.

4. waiter_command = بأمر مباشر من جرسون الطلبات
-----------------------------------------------
الأثر:
- جرسون الطلبات يبدأ التنظيف يدوياً.
- مناسب عندما الكابتن مسؤول عن دورة الطاولة كاملة.

25) إعدادات الجهاز المشترك والـ PIN
============================================================

صفحة:
- إعدادات تشغيل نقطة البيع

الفكرة:
- هل الجهاز مخصص لمستخدم واحد أم مشترك بين أكثر من جرسون؟
- عند التفعيل، بعض العمليات الحساسة تحتاج PIN أو terminalToken صالح.

أ) طريقة استخدام نقطة البيع
---------------------------

1. جهاز مستقل لكل مستخدم
-------------------------
الأثر:
- جلسة دخول عادية.
- لا overlay PIN.
- مناسب للأجهزة الشخصية أو جهاز لكل موظف.

2. جهاز مشترك بين كل الجرسونات
------------------------------
الأثر:
- يطلب PIN قبل العمليات الحساسة وعند الخمول وتبديل المستخدم.
- السيرفر يرفض بعض المسارات لو لم يصل terminalToken صالح.
- المطور مستثنى لتسهيل التهيئة.

مناسب لـ:
- جهاز واحد على الصالة يستخدمه أكثر من جرسون.

ب) نمط القفل
-------------

1. هجين منزلق - موصى به
-----------------------
الأثر:
- العمليات الروتينية لا تقفل بعد كل مرة.
- لكنها تجدد عداد الخمول.
- العمليات الخطرة تطلب PIN داخل الزر Step-Up.
- الخمول الطويل يظهر overlay.
- الإهمال الأطول يخرج المستخدم بالكامل.

مناسب لـ:
- توازن بين السرعة والأمان.
- التشغيل اليومي في الذروة.

2. قفل بعد كل عملية - كلاسيكي
------------------------------
الأثر:
- بعد كل حفظ/إرسال/تعديل/حذف/خصم/مرتجع حسب المفاتيح المختارة يطلب PIN.
- أكثر أماناً لكنه أبطأ.

مناسب لـ:
- بيئة تحتاج رقابة شديدة.

ج) إعدادات النمط الهجين
-----------------------

- idleLockMinutes:
  عدد دقائق الخمول قبل ظهور overlay قفل.

- hardLogoutMinutes:
  عدد دقائق الإهمال قبل خروج كامل من التطبيق.

- tokenTtlSeconds:
  مدة صلاحية حداثة PIN أو terminalToken.
  النطاق في الكود: 60 إلى 7200 ثانية.

- stepUpForDangerOps:
  عند on: العمليات الخطرة تطلب PIN فوري داخل الزر.
  عند off: تعتمد أكثر على overlay أو التحقق العام.

د) محفزات القفل في الوضع الكلاسيكي
----------------------------------

المفاتيح:
- lockAfterSave
- lockAfterEdit
- lockAfterSend
- lockAfterDelete
- lockAfterDiscount
- lockAfterReturn

الأثر:
- كل مفتاح on يعني أن العملية المقابلة تقفل الجهاز بعدها.

هـ) سياسة محاولات PIN
---------------------

- maxAttemptsBeforeLockout:
  عدد المحاولات الفاشلة قبل قفل مؤقت.
  النطاق: 1 إلى 20.

- lockoutSeconds:
  مدة القفل بعد الفشل.
  النطاق: 5 إلى 900 ثانية.

الافتراضي:
- 3 محاولات.
- 30 ثانية قفل.

26) سياسة الضريبة والخدمة
============================================================

صفحة:

المفاتيح:

أ) خدمة %
---------
الأثر:
- نسبة الخدمة التي تضاف على الفاتورة.
- الافتراضي في الواجهة: 12.5

ب) VAT %
--------
الأثر:
- نسبة ضريبة القيمة المضافة.
- الافتراضي في الواجهة: 14

ج) الخصم قبل الضريبة
--------------------

true:

false:

-----------------

true:
- يضيف الخدمة ثم يحسب VAT عليها أيضاً.

false:
- الخدمة لا تدخل بنفس الطريقة في وعاء VAT.

- تغيير هذه الإعدادات يغير أرقام الفواتير، لذلك لا يغير أثناء اليوم بدون قرار واضح.

28) أمثلة عملية لاختيار 1 أو 2
============================================================

مثال 1: إلزام الجدولة
----------------------
- off:
  أحمد يدخل كـ waiter حتى لو المدير لم يضعه في جدول اليوم.

- on:
  أحمد لا يدخل كـ waiter إلا لو له صف في جدول اليوم.
  إذا لا يوجد صف تظهر رسالة: أنت لست ضمن فريق العمل اليوم.

مثال 2: قفل الطاولة على كابتن
-----------------------------
- off:
  أي waiter يضيف طلبات على الطاولة.

- on:
  فقط الكابتن المسكّن يضيف الطلبات ويطلب الحساب.
  المدير يستطيع التدخل.

مثال 3: من يستلم من المطبخ
--------------------------
- server:
  المناولة مسؤولة عن خروج الأصناف للطاولات.

- waiter:
  نفس الكابتن يتابع المطبخ والتوصيل.

مثال 4: بداية التنظيف
---------------------
- request_check:
  بمجرد طلب الحساب تبدأ الطاولة تدخل مسار التنظيف.

- payment_completed:
  بعد إتمام الدفع فقط تبدأ الطاولة مسار التنظيف.

مثال 5: الجهاز المشترك
----------------------
- جهاز مستقل:
  المستخدم يدخل ويعمل بدون PIN متكرر.

- جهاز مشترك:
  العمليات الحساسة والخمول وتبديل المستخدم تحتاج PIN.

مثال 6: نوع المنشأ
------------------
- مطعم:
  الافتراضي طاولة.

- كوفي شوب:
  الافتراضي سفري.

30) نقاط حذر قبل تغيير الإعدادات
============================================================

1. لا تفعل enforceRoleScheduleForShift قبل إدخال جدول اليوم للجرسونات.
2. لا تفعل orderTakerExclusiveTable إلا بعد تدريب المستخدمين على تسكين الكابتن.
3. لا تغير سياسة الضريبة والخدمة وسط اليوم بدون مراجعة أثرها على الفواتير.
4. لا تختار kitchenOutputMode = printers فقط قبل ربط الطابعة فعلياً.
5. لا تستخدم cost_plus للـ VIP إلا إذا بيانات التكلفة صحيحة.
6. الجهاز المشترك يزيد الأمان لكنه قد يبطئ التشغيل إذا اختير نمط كلاسيكي شديد.
7. قوالب Owner/VIP تعتمد على وجود عملاء فعليين في TBL016 ضمن مجموعة owners&vip.

============================================================
31) قائمة فحص يومية للمدير
============================================================

قبل بداية اليوم:
1. راجع جدول أدوار المستخدمين.
2. إذا كان إلزام الجدولة مفعلاً، تأكد أن كل waiter/host/server/speed_order لديه صف اليوم.
3. تأكد أن الكاشير والمدير يستطيعون الدخول.
4. راجع هل الجهاز مشترك أم مستقل حسب واقع التشغيل.
5. راجع أن سياسة الضريبة والخدمة صحيحة ولم تتغير.
6. راجع المطبخ: شاشة فقط أم طباعة.
7. راجع قوالب VIP إذا يوجد حجوزات أو عملاء مهمون.

أثناء اليوم:
1. إذا ظهر لمستخدم: أنت لست ضمن فريق العمل اليوم، راجع جدولة الدور.
2. إذا جرسون لا يستطيع العمل على طاولة، راجع قفل الكابتن وتسكين الكابتن.
3. إذا لا تظهر قوالب VIP، راجع TBL015/TBL016 وقوالب Owner/VIP.
4. إذا PIN يزعج التشغيل، راجع إعدادات الجهاز المشترك ونمط القفل.
